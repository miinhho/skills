# Widgets and Accessibility Contract Verification

## What to verify for every widget

For each widget, document **initial state → key input → where focus lands → changes to role, name, state, and appearance → where focus lands after leaving**. Enter with Tab or Shift+Tab and check internal navigation and activation with the keys appropriate to the widget. Check that focus is visible and unobscured and does not move to hidden descendants or background content. Do not substitute mouse clicks or programmatic focus in test code for the keyboard flow.

If your existing test tools support it, query by both role and accessible name, then verify the relevant state and focus location. For example, check that a closed dialog is absent from the default role query, and that immediately after opening it with the keyboard, focus is inside the dialog whose accessible name matches its title. Tests that check only DOM classes or portal container IDs can pass even when users lose access to those semantics. For widgets that share a pattern, use data-driven tests to verify their role, name, opening, and closing contracts. Match labels and states to the language users see and the intended behavior of each widget. Check paths with different behavior separately, such as errors, dynamic removal, or two instances.

Role-based queries are useful for checking native semantics and accessible names, but they only show that the implementation meets the tool's model. Do not report keyboard paths or screen reader announcements as verified on the basis of a query that forcibly includes hidden elements, a static snapshot, or a single automated audit. If announcement wording or timing is at issue, check the state transition with actual assistive technology.

## Tabs: Distinguish page navigation from panel switching

**When to use:** Consider tabs when users activate one of several associated panels on the same screen. If the list is for page navigation, keep the links even if they look like tabs, and use `aria-current="page"` on the current link if needed. Do not decide based only on whether the URL changes. Check whether the user is navigating between pages or choosing a panel within the same widget.

**Implementation:** For the tabs pattern, give the `tablist` a name and keep the `tab` elements' `aria-selected` states in sync with the active panel. Point each tab's `aria-controls` to its corresponding `tabpanel` and each panel's `aria-labelledby` back to its tab. Use `hidden` or an equivalent mechanism to remove inactive panels from view, focus order, and assistive technology navigation. Updating only `aria-selected` or relying on `aria-hidden` alone can leave descendants focusable.

**Keyboard behavior and regression checks:** Tab into the list at the selected tab and use the arrow keys to move within it. Use Left and Right for horizontal lists, and set `aria-orientation="vertical"` and use Up and Down for vertical lists. Keep the tab list a single Tab stop, and let Tab leave the group for the active panel or the first interactive element inside it. If a panel starts with content to read, the panel itself can be in the Tab order. Automatic activation is appropriate when panels appear without delay. If loading is slow or switching is costly, use the arrow keys to move focus only, then Enter or Space to activate the tab. With manual activation, the focused tab and selected tab can differ. Check state and panel exposure after arrow-key navigation and activation. Also check that leaving the group without activating a tab and then returning still puts focus on the selected tab.

## Modals: Check from opening through dismissal

**When to use and how to implement:** Use a modal when users must be prevented from interacting with the background. If your supported environments allow it, first consider opening a `<dialog>` with `showModal()`. Opening a dialog with only `show()` or the `open` attribute does not provide the same modal behavior. Associate the visible title through `aria-labelledby`. For a custom modal, implement focus management and block background interaction in addition to setting `role="dialog"` and providing a name. Declare `aria-modal="true"` only if background interaction is actually blocked. If you use `inert` on the background, check that the modal is not a descendant of that background and that the previous state is restored when the modal closes or is removed. `aria-hidden` alone cannot block focus or clicks.

**Focus lifecycle:** Remember the entry point before opening, and choose an initial focus target appropriate to the content. The heading at the start of lengthy content or the less risky button for a destructive action may be appropriate. Check that Tab and Shift+Tab do not reach the background page. Provide a discoverable close button and let users close the modal with Escape. After closing, usually restore focus to the entry point. If that element was removed or the action produced a more natural target, move focus there instead. If you support nested modals, check that closing one restores focus to its parent modal without prematurely re-enabling the background.

**Regression checks:** Activate the opening button with the keyboard and check the dialog's name and initial focus. Navigate in both directions within the dialog and check dismissal with the close button and Escape separately. After closing, check that background interaction resumes and focus returns to the right place. If you support variants such as removal of the entry point, check the alternate focus target as well. Native behavior does not automatically guarantee the outcome when combined with the app's portals, conditional rendering, or event handling.

For other composite widgets, check the [WAI-ARIA APG pattern](https://www.w3.org/WAI/ARIA/apg/patterns/) that matches the actual behavior. For example, a select-only list and an editable combobox have different focus and selection models. If a native `<select>` is sufficient for simple selection, do not add the contract of a custom widget.
