# Semantics and Forms

## Match roles to actual behavior

When you see a clickable `<div>`, an `href="#"` that runs a command, or a button inside a link, first identify the action the user takes. Use a link with a real destination for navigation. Use a button for commands such as saving, opening, or deleting. If a card needs both a details link and a separate menu button, make them siblings in the same container and give each a visible focus indicator. Stopping event propagation does not fix invalid nesting.

For checkboxes, radio buttons, select lists, and simple disclosures, start by considering `<input type="checkbox">`, `<input type="radio">`, `<select>`, and `<details>/<summary>` as appropriate. For example, use `checked` to manage whether a checkbox is selected. Do not replace a link that users can open in a new tab with Cmd/Ctrl+click with a button, or add a separate tab stop to a container with no semantic purpose. Choose a widget pattern only when native semantics and behavior do not meet the requirements.

Use `disabled` when the element supports native disabling and the contract calls for removing it from keyboard focus. If disabled items must remain discoverable within a composite widget, `aria-disabled="true"` may be appropriate. This attribute alone does not block activation or navigation, so check that each input path enforces the intended restrictions. Align DOM order with reading and focus order rather than using positive `tabindex` values to correct the order. `tabindex="-1"` lets code move focus to the element without adding it to the normal Tab order.

## Distinguish names, descriptions, and visual cues

- Associate form inputs with visible `<label>` elements. Check that the label's `for` matches the `id` of the actual input and that IDs do not collide when multiple instances appear on the same screen. Use `<fieldset>` and `<legend>` to give related radio buttons or checkboxes a shared context.
- When a button or link has sufficient visible text, use that text as its name. Use `aria-labelledby` to reuse an existing heading or label. If there is no visible name, as with an icon-only button, provide text or an `aria-label` that conveys the purpose. When there is a visible label, make sure the computed name includes its wording. A `placeholder` gives an example of what to enter; it is not a persistent label.
- Use `aria-describedby` when supplementary information, such as an input format or the result of an action, needs to be associated with a control. Do not pack all the instructions into the name or redundantly expose decorative icons. Give informative images alternative text that conveys what matters in context, and use `alt=""` for decorative `<img>` elements. Provide text or another cue for states otherwise distinguished only by color.

## Form submission and error reporting

**Keep submission a form action.** Associate the inputs and `<button type="submit">` with the `<form>`, and handle submission through the form's submission path rather than a click-only button handler. A button outside the form can use its `form` attribute to reference a form ID in the same document. Use `type="button"` for commands inside the form that do not submit it. Implicit submission with Enter depends on the form's structure and input types, so check the intended inputs. If code needs to use the same submission path as a user, consider `requestSubmit()`. The `submit()` method bypasses constraint validation and the `submit` event.

**Separate who validates from when errors are shown.** Keep native behavior when HTML constraints such as `required` and `type="email"` are sufficient. If native constraint validation blocks submission, the `submit` handler may not run. Do not rely on that handler alone to display errors. If you use `setCustomValidity()`, clear the message with an empty string when the error is resolved. If you use `novalidate` to display custom errors, specify what validation and guidance the app takes responsibility for on submission. Input constraints do not replace server validation.

**Preserve the existing submission and failure contract.** Do not change the submit function's arguments or return value, existing exception handling, or what happens after success just to associate accessibility information. Associate existing server error state with the field and update it when the error is resolved or no longer applies to the previous input. If an example does not specify server handling, leave the existing handler as is and explain only where to set and clear error state. Do not assume a separate response format.

**Associate actual errors with their fields.** Do not mark empty required fields as invalid on initial display. Show format errors when users can act on them, such as after they finish entering the value or try to submit. Show missing-value errors for required fields after a submission attempt. Set `aria-invalid="true"` only when the app displays an error state, and remove the attribute or set it to `false` when the error is resolved. Do not assume that native validity or `:user-invalid` always matches this display policy.

- Show text that explains what went wrong and how to fix it. If you associate the error with the field through `aria-describedby`, keep existing hint references. Alternatively, check support in the target environment and use `aria-errormessage` to reference the visible error when `aria-invalid="true"`. Do not automatically reference the same error from both attributes. Update the error reference and display when the error is resolved.
- **Implement field association separately from submission failure announcements.** Do not assume attributes that associate an error with an input will notify users of a new error when focus remains on the submit button or a server error arrives later. If there is no existing announcement path, respond to the error by moving focus to the first invalid field or an error summary, or by updating the text of a live region rendered in advance. Include the chosen announcement path in code examples. Let users move from the summary to the fields, and do not steal focus on every keystroke or announce the same error twice through both paths.

**Regression checks:** Verify this as one flow: initial display → submit an invalid value → find and fix the error → resubmit. At each step, check the field's name, description, and error state separately from announcements, focus location, and submission results. Do not conclude that an error is associated with a field or announced by assistive technology just because its text appears on screen.
