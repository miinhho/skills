# Debugging data flow, lifecycle, and performance

## Results get mixed up or requests are duplicated

- Correlate the value at the time of input, request IDs or keys, request start and completion order, which responses were applied, and the values shown on screen. Distinguish multiple request starts from multiple applications of a single result. An incorrect response, a cache key collision, a stale callback value, and an overwrite by a late response can look alike on screen. An HTTP success status does not prove that the response applied was the right one for the current view.
- If you suspect ordering, use responses whose completion you can control. Keep the input and data fixed and reverse only the completion order. For duplicate requests, trigger the second request for the same key before completing the first. This isolates the race more clearly than fixed waits or repeated refreshes. If test responses replace a suspected cache, transformation, or routing layer, the test does not verify that layer.
- If only the latest selection is valid for the view, check whether the request is still current at the boundary that writes state. Cancellation can reduce waste when the operation supports it, but check separately whether it protects against work that has already finished or downstream steps that do not honor cancellation. Do not apply this rule indiscriminately where state must be merged or independent work must run concurrently. If duplicate execution is the cause, prevent it where the owner decides whether the same work is already in progress. After the fix, check any late success or failure path that could overwrite state, as well as normal completion of the current request.

## Resources accumulate when a view is closed or reopened

- Record when the route or view starts and ends, and pair creation with cleanup for listeners, subscriptions, timers, observers, and requests. Verify rather than assume that closing or hiding a view unmounts it. With the same data, repeat opening, closing, and reopening the view, and check for callbacks from closed instances or count the resources that remain.
- Distinguish a temporary rise in memory use, intentional caching, and references that remain live. Compare runs with the same number of repetitions, data, and observation point. If heap snapshots are available, account for differences in garbage collection timing and identify which references retain the closed instance. Do not infer missing cleanup from a memory graph alone.
- Have the owner that acquired the resource release it at the lifecycle boundary where cleanup was missed, using the same handle or the cleanup function returned during registration. Do not shut down a shared resource globally while other views still use it. Verify that the resource no longer runs after closing and that reopening recreates only the subscriptions the view needs.

## A particular interaction stutters or slows down

- Translate “slow” into an observable result, such as latency from input to the visible update, dropped frames, or time to finish loading. For the affected interval, compare time spent on main-thread work, framework rendering, style calculation, layout and paint, or network waits. Render count alone does not explain user-visible latency.
- Establish a baseline using the build mode, device, data size, and interaction interval where the symptom occurs. Keep the device and conditions fixed, make one change, and compare metrics over the same interval. Do not mix measurements taken with different cache or warm-up states. Traces from a development build or throttled desktop environment can guide the investigation but cannot substitute for observing behavior that occurs only on the actual device.
- Reduce work only at the measured bottleneck. Instrumentation can itself change timing, so compare under the same instrumentation conditions and state the scope of the observation. Do not add memoization or restructure rendering before narrowing down the candidates. After the fix, check not only the measurements but also that the previously slow interaction has the same result and final state.
